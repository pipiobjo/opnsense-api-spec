# 0006: Consumers need a capability layer

Status: accepted, planned

## Context

Measured on 26.7 (2026-11-10): writes with unknown keys return
`{"result":"saved"}` and change nothing for those keys: invented fields,
invented sections, fields at an old location
(`unbound.dnsbl.safesearch`), and even a wrong wrapper key (whole payload
ignored). Only known fields with invalid values fail.

OpenAPI has no notion of availability per server version, and generated
clients ignore the meaning of `x-` extensions. A generic client therefore
sends unsupported fields without any error, which is exactly how a moved
field went unnoticed in a Terraform provider.

## Decision

- The spec carries the data: fragments and their availability, per-field
  and per-enum-value availability, moved-from information.
- Consumers (our Go client and provider) get a thin capability layer
  generated from that data: detect `product_version` and installed plugin
  versions, select fragments, and reject unsupported operations, fields and
  values before sending.
- Providers keep one stable schema across versions and map moved fields per
  detected version.

## Consequences

- Silent no-ops become errors at plan/request time.
- Version detection needs `/api/core/firmware/info` over HTTP/2: its large
  response is sometimes cut over HTTP/1.1 (intermittent; seen again on
  26.7.9_3 on 2026-11-17).
- Clients generated by third parties from the plain spec do not get this
  protection; the concepts document says so.
