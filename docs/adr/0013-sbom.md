# 0013: Software bills of materials

Status: accepted 2026-11-17; built and checked in every dry run, published
once the repository variable `SBOM_PUBLISH` is `true`

## Context

Requirement Q7: quality evidence must be visible, including software
bills of materials. Two things are worth describing here:

- The **published releases** are derived from OPNsense packages. Which
  packages, in which version and with which checksum, is the supply chain
  of the data, and nothing outside this repository knows it.
- The **generator** is a Go program with five direct dependencies.

## Decision

- Each release gets `opnsense-<release>.sbom.cdx.json` (CycloneDX 1.6):
  the API description as the main component, every package it was derived
  from as a component, with its hash from the signed catalog (pkg's
  BLAKE2b-512 decoded to hex, or SHA-256 in older catalogs), source commit,
  and the catalog's checksum and signing key as properties. Written by the
  command `sbom` from the IR, so no tool outside this repository is
  involved. Licences are not recorded in the IR and are left out, not
  guessed (ADR 0002).
- The file is deterministic (no timestamp; the serial number is derived
  from the content). An unchanged release keeps an unchanged
  `SHA256SUMS` and is not republished.
- The generator's SBOM is made with the official CycloneDX generator for
  Go (`tools/ci/sbom.sh`, the same script as in opnsense-api-go), run
  isolated in rootless Podman. It belongs to the generator version, not
  to the OPNsense releases (otherwise every dependency update would change
  all of them): a new tag `v<generator>` gets a GitHub release with that
  SBOM.
- Both are covered by `SHA256SUMS` and the provenance attestation.
- Publishing is switched separately (`SBOM_PUBLISH`), because the first
  live run republishes every release once with the new file.

## Alternatives considered

| Option | Why not |
|---|---|
| A generic SBOM tool on the release files | it sees JSON files, not the OPNsense packages they came from |
| Our own generator for the Go modules too | more code to own; the official tool is maintained and runs isolated |
| The generator SBOM in every OPNsense release | every dependency update would republish all releases |

## Consequences

- Consumers can check which packages a description came from with
  standard SBOM tools, and match the generator's dependencies against
  vulnerability databases.
- One more third-party tool in the build, pinned and isolated.

## Evidence

- `TestForRelease`: valid against the official CycloneDX 1.6 JSON Schema
  (vendored in `internal/sbom/testdata`), hashes equal the real
  BLAKE2b-512 of the data, byte-identical on a second run; seen failing
  for an unknown hash algorithm name and an unknown component type.
  `TestSumHash` checks the decoder against real digests.
- All 34 releases (2026-11-17): 34 SBOMs, each valid against the schema,
  identical on a rerun; 99 to 107 packages each.
