# Concepts

This document explains why this project exists, where its information comes
from, how outputs are identified and versioned, how correctness is checked
and what consumers must take care of. It assumes no knowledge of OPNsense
internals or of this project's history.

Every section is marked **implemented** or **planned**. Decisions are
recorded in [docs/adr/](adr/).

## 1. The problem

OPNsense has a large REST API (around 2,500 operations with plugins), but no
machine-readable description of it:

- The truth lives in PHP controllers and XML model definitions inside the
  firewall's packages.
- The API reference on docs.opnsense.org is generated by hand from the
  `master` branch of the source repositories. It is not tied to any
  release, and the commit hash shown on the pages belongs to the
  documentation repository, not to OPNsense.
- Several projects (API clients, Terraform/OpenTofu providers, MCP servers)
  therefore rebuild the same knowledge again, each for one language and
  usually without a link to a specific OPNsense version. Where a spec
  exists, it is bundled with one client implementation.

Consequences seen in practice: fields written to a location that moved in
a newer release are silently ignored (see 7.1), and tools cannot say which
OPNsense version they support.

**Goal:** a versioned, language-independent API description (OpenAPI)
derived from what OPNsense actually ships, with its limitations visible to
the user, and verified against running instances.

**Non-goals:** clients, SDKs, a CLI, a documentation website, tests against
anyone's production firewall.

## 2. Source of truth (implemented)

The input is the official package repository (`pkg.opnsense.org`), not the
git history and not the documentation.

- Each release series has its own repository:
  `/<FreeBSD ABI>/<series>/latest`, e.g. `/FreeBSD:15:amd64/26.7/latest`.
  Core and all plugins in it are built together for that series.
- Per patch release there is a snapshot:
  `/<ABI>/<series>/MINT/<release>/latest` (see 5 for why "snapshot" is not
  the same as "immutable").
- A signed catalog (`packagesite.pkg`) lists every package with version,
  checksum and build commit. Packages are tar archives (zstd, older: xz).
- The packages contain exactly the files that run on a firewall:
  model XML (`mvc/app/models/...`), field type classes, API controllers
  (`mvc/app/controllers/.../Api/*Controller.php`) and migrations.

Why packages and not git tags: packages are what users run, including
plugins (separate repository, separate versions) and hotfix revisions that
have no git tag.

## 3. Trust chain (implemented)

1. A known OPNsense signing key verifies the catalog signature, exactly as
   FreeBSD `pkg` does (RSA PKCS#1 v1.5 over the hex SHA-256 of
   `packagesite.yaml`).
2. Every package is checked against its catalog checksum (BLAKE2b-512 in
   pkg's base32 encoding, or SHA-256 in older catalogs).
3. Key list: taken from the verified core package
   (`/usr/local/etc/pkg/fingerprints/OPNsense/{trusted,revoked}`).
   OPNsense rotates the key per series; older series are signed with their
   own (now "revoked") key. A revoked key is accepted only for series older
   than the one whose core revoked it (`revoked_in` in the key list), so a
   retired key cannot sign a new release.

**Key rotation (implemented).** OPNsense builds a signed chain: the last
patch release of a series already trusts the next series' key (e.g. 25.7.11
trusts the 26.1 key, 26.1.11 trusts the 26.7 key). Before verifying any
catalog, every run walks the series in ascending order and reads the key
lists of the newest release of each series; a key is added only if the
core package listing it comes from a catalog signed by an already known
key. Known keys may move from trusted to revoked, never back (older cores
still list keys as trusted that newer ones revoked); a revocation records
the series of the core that lists it (the earliest wins). The list lives in
`internal/pkgrepo/keys.json` (built in, extended with the source of each
key). If the chain breaks (e.g. an emergency rotation), the run stops with
"unknown key".

Test VM images (section 8) are verified separately: SHA-256 against the
mirror and against the release announcement in `opnsense/changelog`, and
an OpenSSL signature with the release key, which must match the key in the
series announcement.

## 4. Pipeline (implemented)

```
catalog + packages ──► extract ──► IR (JSON) ──► render ──► OpenAPI + coverage
   (verified)          models,       per release              per release
                       field types,
                       controllers
```

- **Models:** every field with type, base class, read shape, required,
  default, options. Field type classes are followed up to the core base
  classes, including overrides of how a field is read back.
- **Controllers:** actions, parameters, inheritance, calls to the generic
  helpers (`searchBase`, `getBase`, `addBase`, `setBase`, `delBase`,
  `toggleBase`) with their wrapper key and model path, overridden hooks.
- **IR:** the language-neutral intermediate representation. It is the
  product's core; OpenAPI is one rendering of it.

## 5. Identity and versioning

### 5.1 Moving targets

| What changes | How often | Effect |
|---|---|---|
| New patch release (`26.7.8`) | about every 2 weeks | new snapshot |
| Hotfix revision within a release (`26.7.8` -> `26.7.8_2`) | irregular | **core files change under the same release number** |
| Plugin updates within a release | irregular | plugin files change |
| The newest snapshot of a series | continuously | `MINT/<newest>` is the live `latest` repository until the next patch release |
| Older snapshots | at the end of their lifetime | contain the last hotfix of that release |
| Series (`26.7` -> `27.1`) | twice a year | new FreeBSD ABI possible, new signing key |
| Package formats, checksum formats | rarely | already changed once (xz -> zstd, SHA-256 -> BLAKE2b) |
| OPNsense MVC framework internals | slowly (an ongoing migration away from Phalcon is visible in the source) | derivation rules may stop matching |
| This generator | with every fix | all outputs need a rebuild |

### 5.2 Model (implemented, except where noted)

Two independent version axes: **input** (OPNsense content) and
**generator**.

- **Fragments.** The unit is one API fragment per API content: one for the
  core, one per plugin. Its identity is a hash over the *derived* API (after
  resolving core field types and base classes), not over the package
  version or the raw files. Measured on real data:
  - the same plugin version has an identical API across releases and even
    across series (`os-haproxy` 5.1: one fragment in 18 releases);
  - package revisions often do not change the API (`os-nginx` 1.36_1 ->
    1.36_5);
  - but an identical version number does not guarantee an identical API
    (`os-crowdsec` 1.0.12 differs between 25.7.11 and 26.1.6);
  - the same plugin files can still yield a different API on a core whose
    field type classes changed; hashing the derived API covers this.
  - Across the 33 releases from 25.7 to 26.7.8: 2,379 fragment references,
    209 distinct fragments. The core changes in every release.
- **Compositions.** A release view is the set of fragments one catalog
  state lists. Identifier: core package version including the hotfix
  revision plus the first 12 hex digits of the catalog hash, e.g.
  `26.7.8_2~e21973a477a4`. Every catalog state seen is kept.
- **Status.** `provisional` while the snapshot is still live (newest
  release of a series; this also applies to older series, e.g.
  `26.1.11_10`), `final` once the next patch release exists. The status is
  updated on every run.
- **Change detection.** Catalogs are always downloaded (packages are cached
  and checked against the catalog checksums). A release is rebuilt when its
  catalog hash or the generator version differs from its current
  composition; otherwise only the status is updated.
- **Determinism.** The same inputs and generator version produce
  byte-identical outputs (tested).
- **Generator versions.** A new generator version rebuilds the current
  catalog state of every release; fragments are content-addressed, so
  unchanged APIs keep their hash and file. Older catalog states (an
  earlier hotfix revision of a release) are not rebuilt, because their
  package files are no longer on the mirror. The capability data leaves
  them out when their release has a state built by the current generator
  (a firewall on such a revision uses the release's current state, as
  for any revision the data does not list); `dist/` keeps them. A change
  of the derived API without a new generator version fails the golden
  test (`TestGeneratorRule`).

Layout of `dist/`:

```
fragments/common/<hash>.openapi.json          shared schemas
fragments/<package>/<hash>.ir.json            one fragment (IR)
fragments/<package>/<hash>.openapi.json       one fragment (OpenAPI, refs to common)
<release>/composition.json                    current catalog state
<release>/compositions/<id>.json              every catalog state seen
<release>/opnsense-<release>.{ir,openapi}.json release view (self-contained)
<release>/<previous>..<release>.{json,md}     changes to the previous release
index.json                                    releases, compositions, fragment availability
```

## 6. Derivation levels and transparency (implemented)

The generator never guesses. Every operation carries
`x-opnsense-derivation`:

| `source` | Meaning |
|---|---|
| `base` | generic base-class action (`getAction`, `setAction`, service actions) on the bound model; typed |
| `base-call` | the action returns a generic helper's result directly; typed |
| `signature-only` | only path and parameters are known; untyped |

`gaps` lists what the generator noticed but could not resolve, as
`{"code": ..., "detail": ...}`. Behaviour (of this generator and of
consumers) must depend only on the stable `code`; `detail` is for humans
and may be reworded. Operations with `source: signature-only` are never
typed, whatever their kind.

| Code | Meaning |
|---|---|
| `custom-action` | own action; request and response not derived |
| `http-method-unknown` | HTTP method not derivable |
| `override-calls-parent` | overrides a generic action and calls the parent; may return a subset or extra keys |
| `override-not-derived` | overrides a generic action without the parent; untyped. The root key is the one its code shows, or none (then the operation is an action in the capability data) |
| `service-override` | overrides a generic service action |
| `get-model-nodes-override` | `getModelNodes` overridden; `get` may return a subset |
| `custom-logic` | own code around a generic helper |
| `post-processed` | the helper result is transformed before it is returned |
| `result-not-returned` | the action calls a helper but does not return its result; the response is empty (an upstream quirk, e.g. `os-wol` `delHost`) |
| `helper-used-internally` | custom action that uses a helper internally; untyped |
| `multiple-helpers` | several helper calls; the one matching the action is documented |
| `helper-non-literal` | helper called with non-literal arguments; untyped |
| `custom-write` | (field) the field type, or one it inherits from, overrides `setValue`: the stored value may differ from the request (normalized, encoded, converted). Core normalizers count too (`HostnameField`, `NetworkField`, `PortField`, `MacAddressField`, ...) |
| `custom-save` | (model, entry list or write operation) own code between the request and what is read: the model class overrides `serializeToConfig` or `init` (the setup wizard loads every value from the rest of the configuration), the entries are stored through `toLegacy`/`fromLegacy` (interface assignments), or the controller overrides `save` (os-stunnel sets `general.enabled` from its services). Values may be changed, computed, written elsewhere or dropped depending on other fields; the rule itself is not derived |
| `magic-call` | the controller answers other action names through PHP's `__call` (unbound's `*Dot` endpoints, aliases of `*Forward` with `type` dot); those endpoints are not in the spec |
| `overlay-unknown` | `addBase`/`setBase` force fields through an overlay whose fields cannot be derived (a helper method, an overlay assembled after reading the request, an expression); which fields is unknown |
| `no-apply-endpoint` | no apply/reconfigure endpoint found |
| `parent-missing` | a parent class of the controller was not found in the sources |
| `model-class-missing` | the controller names no model (`$internalModelClass`) |
| `model-missing` | the model the controller names was not found |
| `model-path-missing` | a helper call names a path the model does not have |
| `model-path-not-array` | a helper call for entries names a path that is not an entry list |
| `unknown-setting` | (field) an untyped XML element that is not a known field setting; reported instead of guessed |
| `field-type-unresolved` | field type not resolved to a core base class (field level) |
| `custom-read-shape` | custom `getNodeData`/`getNodeOptions`; read shape untyped (field level) |
| `options-dynamic` | option list depends on the running system (field level) |
| `invalid-default` | default outside the allowed values; an upstream model error (field level) |

Codes counted as "the instance may answer with another shape"
(`override-*`, `service-override`, `get-model-nodes-override`,
`custom-logic`, `post-processed`) turn contract-test mismatches into
`known-gap`, with one narrowing derived from the code itself:
`override-calls-parent` and `get-model-nodes-override` mean the action
returns the generic result with whole sections left out or keys added. On
an endpoint that has only such marks, the shape check is `known-gap` only
when every difference is a missing entry list or container or an added
key; a missing field (for example a renamed one), a value of another type,
a missing root key or an answer that is not JSON stays a `mismatch`. There
is no baseline file to maintain: the rule follows from the gap code and the
model. The other codes describe code the generator does not read, so any
difference in the content there is expected; such resources are marked
`known-gap`, not `ok`, in the capability data. No code explains a missing
root key: the key is derived (a helper's first argument, the model name of
the generic actions, or the key an own settings action uses in its code,
`override-not-derived` included) and published as such; where it cannot be
derived the operation has none, and the contract test does not compare
its shape. The document also carries `x-opnsense-coverage` (gaps counted
by code), and each release has a `coverage.md`.

Further extensions: `x-opnsense-relation` (on relation fields: the model and entry list whose UUIDs are valid values), `x-opnsense-package` (which package provides an
operation, with alternatives), `x-opnsense-apply` (the call that activates
changes), `x-opnsense-name-collision` (field names differing only in case
or `_`), `x-opnsense-verified` and `x-opnsense-runtime-required` (from
contract tests, section 8).

## 7. Conventions of the OPNsense API

Verified against running 26.7 and 26.1.6 instances unless noted.

### 7.1 Unknown keys are ignored silently

A write (`set`, `add`) with a key the model does not know returns
`{"result":"saved"}` and changes nothing for that key. This covers
invented fields, invented sections, fields at an old location (e.g.
`unbound.dnsbl.safesearch`, which moved to `unbound.general.safesearch` in
25.7.8) and even a wrong wrapper key (the whole payload is ignored). Only
known fields with invalid values produce `{"result":"failed",
"validations": {...}}`.

**Consequence:** a client must not rely on the server to reject unsupported
fields. See section 9.

### 7.2 Other conventions

- Changes are stored by set/add/del/toggle but only become active after the
  module's apply endpoint (`x-opnsense-apply`).
- Validation errors come with HTTP 200 (`MutationResult`).
- Read and write shapes differ: list fields are read as
  `{key: {value, selected}}` and written as comma-separated keys.
- PHP encodes maps with keys `0..n-1` as JSON arrays, and empty objects as
  `[]`. An empty entry list in a model `get` is therefore `[]`; the read
  schemas describe it as "UUID map or empty array" (without this, a
  generated Go client fails to decode the whole response).
- Booleans are the strings `"0"` and `"1"`; almost everything is a string.
- The request/response root key is the controller's `$internalModelName`
  for get/set, and the helper's key for entries (`{"blocklist": {...}}`);
  some actions wrap it once more (`{"pac": {"match": {...}}}`).
- A GET with `Content-Type: application/json` and no body is rejected with
  HTTP 400 "Invalid JSON syntax".
- Large responses (e.g. `firmware/info` with many plugins, firewall logs)
  sometimes arrive with broken chunked encoding over HTTP/1.1; over HTTP/2
  they are complete. It is intermittent: an 860 KB firewall log came
  through intact on 2026-11-17, `firmware/info` on 26.7.9_3 was cut the
  same day. Clients should use HTTP/2 (the Go client does). The contract
  test uses HTTP/1.1 on purpose, so the fault stays visible: a read that
  is cut (or reset, or answered with 502/503) is repeated once after a
  short pause and the check records the retry as a note; only a second
  failure fails the check. Writes are never repeated.
- Some required fields are enforced only in PHP validation, not marked
  `Required` in the model (`x-opnsense-runtime-required`).

## 8. Verification

| Layer | Purpose | Status |
|---|---|---|
| Unit tests with fixtures | parser, signature/checksums, classification, rendering, diff, verifier | implemented (`go test ./...`) |
| Live tests on real packages | the parser resolves every model and field type of a real release | implemented (skipped without downloaded sources) |
| Release matrix and diffs | every release from 25.7 on, changes between consecutive releases | implemented |
| OpenAPI validation | every release and fragment document is valid against the official OpenAPI 3.1 schema, and every component schema compiles as JSON Schema 2020-12 (fragments together with their common document) | implemented; stops the build |
| Client functional test | a provider-style scenario with the generated Go client against the test VM: version detection, settings get/partial set/read back, apply, entry add/get/set/search/delete, select fields, validation errors | implemented (`tools/client-smoke.sh <release> --run`, `test/consumer-go/`); 14/14 on 26.7 |
| Response schema validation | every response of the contract tests validated against the rendered OpenAPI schema (JSON Schema 2020-12), not only against the model, so that decoding problems of generated clients show up generically | implemented (`schema` checks in `verify`) |
| Consumer smoke test | a Go client generated with oapi-codegen (pinned v2.8.2) compiles together with the scenario (blocking); openapi-generator for other languages (informational) | Go: in every pipeline run for the newest release of each series (`tools/client-smoke.sh <release>`); openapi-generator: not automated, deferred while all consumers are Go ([ADR 0007](adr/0007-openapi-3-1.md)) |
| Contract tests | every GET against a real instance; per entry list add -> read back -> update -> read back -> list order -> delete with generated values, write-only fields checked to read back empty; per settings model one field changed, read back, restored; all plugins with an API installed | implemented (`tools/testvm.sh`, [ADR 0009](adr/0009-generated-write-values.md)); `verify` exits non-zero on any unexplained finding |
| Golden tests | fragment hashes of final releases (25.7.10, 26.1.10, 26.7.7) checked in; a generator change that alters the derived API of an existing release fails per package | implemented (`internal/assemble`); CI fetches the sources and fails instead of skipping when they are missing (`GOLDEN_REQUIRED=1`) |
| Determinism | two builds from the same sources give identical IR, OpenAPI and fragment hashes | implemented (`internal/assemble`) |
| Invariants | no duplicate paths, every referenced model and package exists, every operation has a method, every local `$ref` resolves; a violation stops the build | implemented (`internal/quality`) |
| Regression report | per release against its predecessor: operations typed -> untyped, field read shapes -> unknown, new gap codes on existing operations (`<prev>..<release>.quality.json`) | implemented; a report, not a gate |
| Framework fingerprint | normalized hashes (comments and whitespace removed) of the core files the derivation relies on, per release; changes listed in the quality report | implemented; a report, not a gate |
| Unknown settings | an untyped leaf element that is not a known setting is reported (`unknown-setting`) instead of becoming a field or vanishing; a typed element is always a field | implemented |
| Verification tracking | the index records which composition was contract-tested (`verified`, `needs_verification`); a run with failures or with untested plugin packages (`untested_packages`) does not count as verified | implemented |
| Contract tests per release | boot the series image, update it through the package proxy to exactly the target release, install all API plugins, test; daily for the newest unverified release of each series, older releases on request | implemented ([ADR 0008](adr/0008-pipeline-and-publishing.md)) |
| Second derivation | compare the endpoint list with OPNsense's own `collect_api_endpoints.py` | planned |
| Generated write values | values from field types and constraints for the fields the server rejects, options from the instance, prerequisite entries for relations; accepted entries become request examples | implemented ([ADR 0009](adr/0009-generated-write-values.md)); 26.7.9: 162 of 188 entry lists pass |

**Contract test environment.** A throwaway VM from the official nano image
under QEMU/KVM, fresh disk overlay per run, isolated user-mode networks
(no route to any LAN or the internet). The only way in is a port forward
on `127.0.0.1`; the only way out is a package proxy that serves nothing
but the signed package snapshot of the VM's release (pinning the snapshot
keeps the repository's core version equal to the installed one, which the
firmware requires before installing plugins). The verifier refuses any
target other than `127.0.0.1`/`localhost`.

### 8.1 Making silent failures loud

The dangerous failure is not "the generator does not understand
something" (that yields `signature-only`, visibly less typed) but "the
generator believes it understands something whose meaning changed".

Measured over 25.7 to 26.7.8, the framework files change in 21 of 32
release transitions, and regressions (typed -> untyped) occur in 6, each a
real upstream change (firewall rule actions rewritten, a new OSPF field
type). A gate on these signals would need a human in two of three
releases. Therefore the contract test is the gate, and the other signals
explain its result:

| Situation | Decision |
|---|---|
| catalog unchanged | nothing |
| invariant violated or key chain broken | do not publish; report |
| new composition (release, hotfix, plugin update, generator) | contract test (automatic) |
| contract test without mismatches outside known gaps and accepted findings | publish; regressions and framework changes go into the release notes |
| contract test with new mismatches | do not publish; report with the quality report (framework changes, regressions) as context |

Accepted findings (known upstream issues or intended behaviour, e.g. the
captive portal client API) are
listed in `verify/accepted.json` with reason, evidence and `match`, the
text of the failure that was reviewed (for example `HTTP 500`); a result on
the same path and check becomes `accepted` only when one of its findings
contains that text, so a different failure there still fails. Entries that
apply to the tested release but covered nothing are listed in the report
(`unused_accepted`) and in the job summary as candidates for removal.
Adding or removing an entry is a reviewed decision.

## 9. Consumers: clients and providers (data implemented; Go client in opnsense-api-go, provider planned)

### 9.1 Views

| View | Use |
|---|---|
| per release (composition) | exact description of one firewall state; scripts, documentation |
| per fragment | one document per core/plugin API, sharing a `common` document |
| capability data per package | all versions merged: resources, fields and actions with the fragments they exist in, and the contract test results; plain JSON, not OpenAPI ([capabilities.md](capabilities.md), ADR 0010) |

Generators handle fragments: oapi-codegen produces one Go package per
fragment and imports shared types from a `common` package (needs
`import-mapping`, and `skip-prune` for the shared document);
openapi-generator resolves the external references and copies the shared
types into each client. A superset is feasible because OPNsense transmits
almost everything as strings: over 33 releases there were 600 added and
41 removed fields, but of 90 type changes 49 only tightened validation
(`TextField` -> `StrictTextField`) and only a handful changed the read
shape.

### 9.2 Capability layer

OpenAPI has no notion of "this field exists from release X", and generated
clients ignore the meaning of `x-` extensions. Because the server ignores
unknown keys (7.1), a generic client would send unsupported fields without
any error. Consumers therefore need a thin capability layer, generated from
the same data:

1. read `product_version` (including the hotfix revision) and the installed
   plugin versions (`/api/core/firmware/info`);
2. select the matching fragments (core version -> framework -> fragment per
   package, [capabilities.md](capabilities.md));
3. reject requests that use operations, fields or enum values this
   instance does not have, before sending them.

### 9.3 Terraform/OpenTofu providers

- one stable schema across versions (from the superset); behaviour follows
  the detected version;
- resources belong to a package: missing plugin -> clear error at plan time;
- attributes with availability: "requires OPNsense >= 25.7.8" at plan time
  instead of a silent no-op;
- moved fields: one attribute keeps its name and maps to the right API
  location per version through the provider's name table; `moved_from` is
  not generated, because OPNsense states moves only in migration code
  ([ADR 0014](adr/0014-attribute-identity-and-moves.md), requirement P8).

## 10. Known limitations

- PHP is read with patterns, not a full parser.
- Options of dynamic list fields (interfaces, certificates, aliases, model
  relations) depend on the running system and are not enumerated.
- OpenAPI version: outputs are 3.1 only ([ADR 0007](adr/0007-openapi-3-1.md)).
  oapi-codegen (>= v2.8.0) and openapi-generator (3.1 "beta") handle it;
  generators may ignore `patternProperties` (display values), which is
  harmless. Known tool-specific issue: openapi-generator's TypeScript
  output fails on enum values such as `~*`.
- Contract tests run daily for the newest release of each series; older
  releases show `needs_verification` until someone requests a test. Some
  entry lists cannot be written automatically (relations to lists without
  an add endpoint, cross-field rules); each is listed with its reason in
  the contract test results.
- Generated Go types: nested sections and union members are named
  components (e.g. `UnboundUnboundGeneralWrite`, `AsSelectOptions()`,
  `AsEmptyList()`); only the response wrappers stay anonymous
  (`JSON200.Unbound`).
- Packages of a release can disappear from the mirror (seen for 26.7.8 in
  November 2026). An earlier build is then kept and marked
  `source_unavailable`; a release that was never built cannot be built.

| contract test | checking the description against a running instance |
