# Concepts

This document explains why this project exists, where its information comes
from, how outputs are identified and versioned, how correctness is checked
and what consumers must take care of. It assumes no knowledge of OPNsense
internals or of this project's history.

Every section is marked **implemented** or **planned**. Decisions are
recorded in [docs/adr/](adr/).

## 1. The problem

OPNsense has a large REST API (around 2,500 operations with plugins), but no
machine-readable description of it:

- The truth lives in PHP controllers and XML model definitions inside the
  firewall's packages.
- The API reference on docs.opnsense.org is generated by hand from the
  `master` branch of the source repositories. It is not tied to any
  release, and the commit hash shown on the pages belongs to the
  documentation repository, not to OPNsense.
- Several projects (API clients, Terraform/OpenTofu providers, MCP servers)
  therefore rebuild the same knowledge again, each for one language and
  usually without a link to a specific OPNsense version. Where a spec
  exists, it is bundled with one client implementation.

Consequences seen in practice: fields written to a location that moved in
a newer release are silently ignored (see 7.1), and tools cannot say which
OPNsense version they support.

**Goal:** a versioned, language-independent API description (OpenAPI)
derived from what OPNsense actually ships, with its limitations visible to
the user, and verified against running instances.

**Non-goals:** clients, SDKs, a CLI, a documentation website, tests against
anyone's production firewall.

## 2. Source of truth (implemented)

The input is the official package repository (`pkg.opnsense.org`), not the
git history and not the documentation.

- Each release series has its own repository:
  `/<FreeBSD ABI>/<series>/latest`, e.g. `/FreeBSD:15:amd64/26.7/latest`.
  Core and all plugins in it are built together for that series.
- Per patch release there is a snapshot:
  `/<ABI>/<series>/MINT/<release>/latest` (see 5 for why "snapshot" is not
  the same as "immutable").
- A signed catalog (`packagesite.pkg`) lists every package with version,
  checksum and build commit. Packages are tar archives (zstd, older: xz).
- The packages contain exactly the files that run on a firewall:
  model XML (`mvc/app/models/...`), field type classes, API controllers
  (`mvc/app/controllers/.../Api/*Controller.php`) and migrations.

Why packages and not git tags: packages are what users run, including
plugins (separate repository, separate versions) and hotfix revisions that
have no git tag.

## 3. Trust chain (implemented; key rotation automation planned)

1. A known OPNsense signing key verifies the catalog signature, exactly as
   FreeBSD `pkg` does (RSA PKCS#1 v1.5 over the hex SHA-256 of
   `packagesite.yaml`).
2. Every package is checked against its catalog checksum (BLAKE2b-512 in
   pkg's base32 encoding, or SHA-256 in older catalogs).
3. Key list: taken from the verified core package
   (`/usr/local/etc/pkg/fingerprints/OPNsense/{trusted,revoked}`).
   OPNsense rotates the key per series; older series are signed with their
   own (now "revoked") key and are accepted and recorded as such.

**Key rotation (planned).** OPNsense builds a signed chain: the last patch
release of a series already trusts the next series' key (e.g. 25.7.11
trusts the 26.1 key, 26.1.11 trusts the 26.7 key). A new key is therefore
accepted automatically only if a core package that lists it as trusted
comes from a catalog signed by an already trusted key. If the chain breaks
(e.g. an emergency rotation), the pipeline stops and reports.

Test VM images (section 8) are verified separately: SHA-256 against the
mirror and against the release announcement in `opnsense/changelog`, and
an OpenSSL signature with the release key, which must match the key in the
series announcement.

## 4. Pipeline (implemented)

```
catalog + packages ──► extract ──► IR (JSON) ──► render ──► OpenAPI + coverage
   (verified)          models,       per release              per release
                       field types,
                       controllers
```

- **Models:** every field with type, base class, read shape, required,
  default, options. Field type classes are followed up to the core base
  classes, including overrides of how a field is read back.
- **Controllers:** actions, parameters, inheritance, calls to the generic
  helpers (`searchBase`, `getBase`, `addBase`, `setBase`, `delBase`,
  `toggleBase`) with their wrapper key and model path, overridden hooks.
- **IR:** the language-neutral intermediate representation. It is the
  product's core; OpenAPI is one rendering of it.

## 5. Identity and versioning

### 5.1 Moving targets

| What changes | How often | Effect |
|---|---|---|
| New patch release (`26.7.8`) | about every 2 weeks | new snapshot |
| Hotfix revision within a release (`26.7.8` -> `26.7.8_2`) | irregular | **core files change under the same release number** |
| Plugin updates within a release | irregular | plugin files change |
| The newest snapshot of a series | continuously | `MINT/<newest>` is the live `latest` repository until the next patch release |
| Older snapshots | at the end of their lifetime | contain the last hotfix of that release |
| Series (`26.7` -> `27.1`) | twice a year | new FreeBSD ABI possible, new signing key |
| Package formats, checksum formats | rarely | already changed once (xz -> zstd, SHA-256 -> BLAKE2b) |
| OPNsense MVC framework internals | slowly (an ongoing migration away from Phalcon is visible in the source) | derivation rules may stop matching |
| This generator | with every fix | all outputs need a rebuild |

### 5.2 Model (implemented, except where noted)

Two independent version axes: **input** (OPNsense content) and
**generator**.

- **Fragments.** The unit is one API fragment per API content: one for the
  core, one per plugin. Its identity is a hash over the *derived* API (after
  resolving core field types and base classes), not over the package
  version or the raw files. Measured on real data:
  - the same plugin version has an identical API across releases and even
    across series (`os-haproxy` 5.1: one fragment in 18 releases);
  - package revisions often do not change the API (`os-nginx` 1.36_1 ->
    1.36_5);
  - but an identical version number does not guarantee an identical API
    (`os-crowdsec` 1.0.12 differs between 25.7.11 and 26.1.6);
  - the same plugin files can still yield a different API on a core whose
    field type classes changed; hashing the derived API covers this.
  - Across the 33 releases from 25.7 to 26.7.8: 2,379 fragment references,
    209 distinct fragments. The core changes in every release.
- **Compositions.** A release view is the set of fragments one catalog
  state lists. Identifier: core package version including the hotfix
  revision plus the first 12 hex digits of the catalog hash, e.g.
  `26.7.8_2~e21973a477a4`. Every catalog state seen is kept.
- **Status.** `provisional` while the snapshot is still live (newest
  release of a series; this also applies to older series, e.g.
  `26.1.11_10`), `final` once the next patch release exists. The status is
  updated on every run.
- **Change detection.** Catalogs are always downloaded (packages are cached
  and checked against the catalog checksums). A release is rebuilt when its
  catalog hash or the generator version differs from its current
  composition; otherwise only the status is updated.
- **Determinism.** The same inputs and generator version produce
  byte-identical outputs (tested).
- **Generator versions.** A new generator version rebuilds everything;
  fragments are content-addressed, so unchanged APIs keep their hash and
  file. Keeping release views of older generator versions side by side is
  **planned**.

Layout of `dist/`:

```
fragments/common/<hash>.openapi.json          shared schemas
fragments/<package>/<hash>.ir.json            one fragment (IR)
fragments/<package>/<hash>.openapi.json       one fragment (OpenAPI, refs to common)
<release>/composition.json                    current catalog state
<release>/compositions/<id>.json              every catalog state seen
<release>/opnsense-<release>.{ir,openapi}.json release view (self-contained)
<release>/<previous>..<release>.{json,md}     changes to the previous release
index.json                                    releases, compositions, fragment availability
```

## 6. Derivation levels and transparency (implemented)

The generator never guesses. Every operation carries
`x-opnsense-derivation`:

| `source` | Meaning |
|---|---|
| `base` | generic base-class action (`getAction`, `setAction`, service actions) on the bound model; typed |
| `base-call` | the action returns a generic helper's result directly; typed |
| `signature-only` | only path and parameters are known; untyped |

`gaps` lists what the generator noticed but could not resolve (overridden
actions, post-processed helper results, custom field read shapes, unknown
patterns, missing apply endpoint). The document also carries
`x-opnsense-coverage`, and each release has a `coverage.md`.

Further extensions: `x-opnsense-package` (which package provides an
operation, with alternatives), `x-opnsense-apply` (the call that activates
changes), `x-opnsense-name-collision` (field names differing only in case
or `_`), `x-opnsense-verified` and `x-opnsense-runtime-required` (from
contract tests, section 8).

## 7. Conventions of the OPNsense API

Verified against running 26.7 and 26.1.6 instances unless noted.

### 7.1 Unknown keys are ignored silently

A write (`set`, `add`) with a key the model does not know returns
`{"result":"saved"}` and changes nothing for that key. This covers
invented fields, invented sections, fields at an old location (e.g.
`unbound.dnsbl.safesearch`, which moved to `unbound.general.safesearch` in
25.7.8) and even a wrong wrapper key (the whole payload is ignored). Only
known fields with invalid values produce `{"result":"failed",
"validations": {...}}`.

**Consequence:** a client must not rely on the server to reject unsupported
fields. See section 9.

### 7.2 Other conventions

- Changes are stored by set/add/del/toggle but only become active after the
  module's apply endpoint (`x-opnsense-apply`).
- Validation errors come with HTTP 200 (`MutationResult`).
- Read and write shapes differ: list fields are read as
  `{key: {value, selected}}` and written as comma-separated keys.
- PHP encodes maps with keys `0..n-1` as JSON arrays, and empty objects as
  `[]`. An empty entry list in a model `get` is therefore `[]`; the read
  schemas describe it as "UUID map or empty array" (without this, a
  generated Go client fails to decode the whole response).
- Booleans are the strings `"0"` and `"1"`; almost everything is a string.
- The request/response root key is the controller's `$internalModelName`
  for get/set, and the helper's key for entries (`{"blocklist": {...}}`);
  some actions wrap it once more (`{"pac": {"match": {...}}}`).
- A GET with `Content-Type: application/json` and no body is rejected with
  HTTP 400 "Invalid JSON syntax".
- Large responses (e.g. `firmware/info` with many plugins, firewall logs)
  arrive with broken chunked encoding over HTTP/1.1 (cut after 64 KiB);
  over HTTP/2 they are complete.
- Some required fields are enforced only in PHP validation, not marked
  `Required` in the model (`x-opnsense-runtime-required`).

## 8. Verification

| Layer | Purpose | Status |
|---|---|---|
| Unit tests with fixtures | parser, signature/checksums, classification, rendering, diff, verifier | implemented (`go test ./...`) |
| Live tests on real packages | the parser resolves every model and field type of a real release | implemented (skipped without downloaded sources) |
| Release matrix and diffs | every release from 25.7 on, changes between consecutive releases | implemented |
| OpenAPI validation | the document is valid OpenAPI 3.1 | planned (blocking) |
| Client functional test | a provider-style scenario with the generated Go client against the test VM: version detection, settings get/partial set/read back, apply, entry add/get/set/search/delete, select fields, validation errors | done manually on 26.7 (14/14 after fixing empty entry lists); automation planned |
| Response schema validation | every response of the contract tests validated against the rendered OpenAPI schema (JSON Schema 2020-12), not only against the model, so that decoding problems of generated clients show up generically | implemented (`schema` checks in `verify`) |
| Consumer smoke test | a Go client generated with oapi-codegen compiles (blocking); openapi-generator for other languages (informational) | done manually; automation planned ([ADR 0007](adr/0007-openapi-3-1.md)) |
| Contract tests | every GET against a real instance, add -> get -> delete per entry list, with all plugins with an API installed | implemented (`tools/testvm.sh`), manual, image versions only |
| Golden tests | fragment hashes of final releases (25.7.10, 26.1.10, 26.7.7) checked in; a generator change that alters the derived API of an existing release fails per package | implemented (`internal/assemble`, needs extracted sources) |
| Determinism | two builds from the same sources give identical IR, OpenAPI and fragment hashes | implemented (`internal/assemble`) |
| Invariants | every helper path exists and is an `ArrayField`, consistent wrappers, known parent classes, no duplicate paths, all references resolve, OpenAPI validates | planned (as build gates) |
| Ratchet baseline | coverage must not regress unnoticed (typed -> untyped, new unknown patterns) | planned |
| Framework fingerprint | hashes of the core files whose semantics the generator relies on; a change requires a passing contract test before publishing | planned |
| Contract tests per release | boot the series image, update it through the package proxy to exactly the target release, test | planned |
| Second derivation | compare the endpoint list with OPNsense's own `collect_api_endpoints.py` | planned |
| Generated write values | test values from field types instead of server defaults | planned |

**Contract test environment.** A throwaway VM from the official nano image
under QEMU/KVM, fresh disk overlay per run, isolated user-mode networks
(no route to any LAN or the internet). The only way in is a port forward
on `127.0.0.1`; the only way out is a package proxy that serves nothing
but the signed package snapshot of the VM's release (pinning the snapshot
keeps the repository's core version equal to the installed one, which the
firmware requires before installing plugins). The verifier refuses any
target other than `127.0.0.1`/`localhost`.

### 8.1 Making silent failures loud

The dangerous failure is not "the generator does not understand
something" (that yields `signature-only`, visibly less typed) but "the
generator believes it understands something whose meaning changed". The
planned defence, in order of strength: contract tests as oracle, framework
fingerprint, invariants, ratchet baseline, golden tests, second derivation.
Pipeline rules:

| Situation | Decision |
|---|---|
| catalog unchanged | nothing |
| changed; invariants hold, no regression, fingerprint unchanged, contract test passes | publish |
| new unknown patterns | publish with affected operations as `signature-only`; report |
| fingerprint changed and contract test shows mismatches | do not publish; report with diff |
| invariant violated or key chain broken | do not publish; report |

## 9. Consumers: clients and providers (planned)

### 9.1 Views

| View | Use |
|---|---|
| per release (composition) | exact description of one firewall state; scripts, documentation |
| per fragment | one document per core/plugin API, sharing a `common` document |
| superset per package | all versions merged, with `x-opnsense-availability` (since/until) per operation, field and enum value, and `x-opnsense-moved-from` for moved fields |

Generators handle fragments: oapi-codegen produces one Go package per
fragment and imports shared types from a `common` package (needs
`import-mapping`, and `skip-prune` for the shared document);
openapi-generator resolves the external references and copies the shared
types into each client. A superset is feasible because OPNsense transmits
almost everything as strings: over 33 releases there were 600 added and
41 removed fields, but of 90 type changes 49 only tightened validation
(`TextField` -> `StrictTextField`) and only a handful changed the read
shape.

### 9.2 Capability layer

OpenAPI has no notion of "this field exists from release X", and generated
clients ignore the meaning of `x-` extensions. Because the server ignores
unknown keys (7.1), a generic client would send unsupported fields without
any error. Consumers therefore need a thin capability layer, generated from
the same data:

1. read `product_version` (including the hotfix revision) and the installed
   plugin versions (`/api/core/firmware/info`, over HTTP/2);
2. select the matching fragments;
3. reject requests that use operations, fields or enum values this
   instance does not have, before sending them.

### 9.3 Terraform/OpenTofu providers

- one stable schema across versions (from the superset); behaviour follows
  the detected version;
- resources belong to a package: missing plugin -> clear error at plan time;
- attributes with availability: "requires OPNsense >= 25.7.8" at plan time
  instead of a silent no-op;
- moved fields: one attribute maps to the right API location per version
  (generated from the diffs, not hand-written).

## 10. Known limitations

- PHP is read with patterns, not a full parser.
- Options of dynamic list fields (interfaces, certificates, aliases, model
  relations) depend on the running system and are not enumerated.
- OpenAPI version: outputs are 3.1 only ([ADR 0007](adr/0007-openapi-3-1.md)).
  oapi-codegen (>= v2.8.0) and openapi-generator (3.1 "beta") handle it;
  generators may ignore `patternProperties` (display values), which is
  harmless. Known tool-specific issue: openapi-generator's TypeScript
  output fails on enum values such as `~*`.
- Contract tests cover the image versions (26.7, 26.1.6) and write paths
  only with server defaults.
- Generated Go types: nested sections and union members are named
  components (e.g. `UnboundUnboundGeneralWrite`, `AsSelectOptions()`,
  `AsEmptyList()`); only the response wrappers stay anonymous
  (`JSON200.Unbound`).
- Not yet automated: the daily pipeline, contract tests per release, the
  superset view and the capability layer (sections 8 and 9).

## 11. Glossary

| Term | Meaning |
|---|---|
| series | `26.1`, `26.7`: a major release line, own package repository and key |
| release | `26.7.8`: a patch release within a series |
| hotfix revision | `26.7.8_2`: a rebuilt core package without a new release number |
| snapshot | `MINT/<release>`: the repository state of a release |
| catalog | `packagesite.pkg`: signed list of all packages of a snapshot |
| plugin | an `os-*` package adding MVC models and controllers |
| model | an MVC model XML: fields, types, defaults, options |
| entry list | an `ArrayField` in a model: entries keyed by UUID |
| wrapper key | the JSON root key of a request/response |
| apply endpoint | the call that activates stored changes |
| IR | intermediate representation, the language-neutral output |
| fragment | the derived API of one package content (planned) |
| composition | the fragments of one catalog state (planned) |
| contract test | checking the description against a running instance |
